# Ten-wallet pilot rehearsal

This is an operator acceptance harness for the **preserved disposable** ten-slot pilot from LOCAL-046. It never creates a genesis, funds a reservoir, resets keys/claims, replaces an invitation or increases capacity. It does not use the real user's local wallet. External devices and real hosted availability remain separate launch gates.

`tools/pilot_cohort_localnet.py` binds to the original accepted `.data/p46a` fixture, its genesis, native binaries, TLS files, runtime activation, funding records and encrypted source/tester wallets. Tester 01/02 reuse the earlier Alice/Bob seeds; the other eight receive separate encrypted wallets/backups. The initial accepted payment already moved 50,000 from Alice to Bob, so the final expected balances are 950,000 and 1,050,000 for those two testers and 1,000,000 each for the remaining eight.

The workload redeems the original ten invitations, interrupts an original grant with full host-group SIGKILL, then lets the serialized native worker finish all ten claims. It verifies every gas grant, the original claim IDs, capped attempts and exactly zero private reservoir balance. It queues one ring payment per tester, with **two local proving/payment jobs active at a time** and ten distinct sends overall. This bounds local CPU use; it is not a ten-proof simultaneous throughput benchmark. Each user signs/pays its own fees through the invited HTTPS gateway; the faucet/operator balance must remain unchanged by those sends.

Both validators independently reconstruct all ten private balances and compare the exact pool/nullifier accounts. The expected permanent nullifiers are 8 at the preserved initial checkpoint, 26 after the nine remaining grants, and 46 after ten new sends. A further host-group crash/restart must preserve the exact state, activation, balances, claims and fee accounts. Concurrent completed-claim retries and restoring tester 10's encrypted seed must recover the same identity/claim without another grant.

Every client operation gets a durable start marker and completion receipt. An uncertain **payment** is never automatically repeated. Pending identities are captured during submission, and native pending/staging journals remain authoritative. Only explicitly idempotent admission/status requests may repeat their original inputs. Failed runs retain their evidence. Resume modes accept specific reviewed admission/cleanup checkpoints and refuse payment replay or unrelated failures; they are not general-purpose repair/reset commands. Once the cohort has progressed beyond its initial checkpoint, do not start the harness again as a fresh run.

## Admission transport resilience

Ten simultaneous admissions exposed the existing four-request faucet listener cap: excess connections closed before an HTTP response. Keep that bound intact. `WalletApp.cli` now retries transport errors only for invited `join`, `access-status` and `test-coins`, using the same wallet, invitation file and stdin password, at most four attempts with exponential backoff and small jitter. It does not retry authorization/quota failures, private sends, withdrawals or payment resolution. TLS validation and all native admission limits remain enforced.

The native CLI binary and protocol are unchanged. The retry is in the wallet server/source runtime used by the local wallet and newly built standalone packages. Existing packaged/installed release artifacts are not silently modified or re-signed. Use the normal reviewed packaging/release process to distribute an updated client.

A Darwin cleanup race also appeared after successful group SIGKILL: a second cleanup signal returned EPERM after the last process had already exited. The harness now accepts that error only when a fresh process-group inspection is empty. A still-live group or different owner remains an error; no administrator permission is requested to bypass it.

The accounting audit must not run `native-wallet balance` on the live faucet's original wallet path. That command holds the wallet's exclusive operation/cache lock; the native grant worker must fail closed if another actor holds that authority's lock. The harness instead uses an owner-only copy of the **encrypted fixture seed** and a separate scan-cache path for balance queries. This is a full encrypted seed copy, not an exported viewing key, and stays inside private local evidence. Original funding/seed bytes and all worker locks remain intact. The live runtime is instrumented only to record bounded native-worker stderr on failure, without changing subprocess results or any pinned code, identity, quota or lifecycle decision.
