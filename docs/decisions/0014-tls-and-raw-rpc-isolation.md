# Local HTTPS and operator-only raw RPC

The invited gateway and faucet terminate TLS directly in their own bounded servers. An HTTPS admission policy requires certificate and private-key inputs and never opens a sibling HTTP listener or falls back to cleartext. TLS handshakes execute inside the existing four-handler bound with a three-second deadline, rather than blocking the accept loop. The minimum protocol is TLS 1.2. Exact audience/Host and browser-Origin checks remain active; forwarded-IP headers are still ignored.

A public profile may include `local_tls_ca_pem` solely for HTTPS endpoints on 127.0.0.1. It contains a public local test CA, never a private key. Clients add that trust certificate while retaining certificate expiry, chain and endpoint-host verification, redirect refusal and disabled proxy discovery. No certificate-verification bypass or machine-wide trust-store modification is introduced. Normal remote HTTPS profiles retain their existing system/web trust behavior and do not use this local development extension. The local CA generator creates a three-day CA and two-day server leaves, plus explicit invalid leaves for tests; it refuses existing output directories. The CA private key stays outside TLS server inputs and tester archives. Renewal under the original CA can replace a server leaf without replacing wallets, profiles or admission records.

Loopback alone does not prevent raw RPC bypass by another local client. A managed private rehearsal can enable a persistent operator-RPC policy before launch. A 256-bit random capability is written to an owner-only regular file, with a separate permanent marker binding its digest and an enabled network configuration. Missing, malformed, shared, symlinked, mismatched or partially restored policy files prevent a managed restart. Neither the network flag nor the marker can silently disappear independently. Existing fixtures remain unchanged unless explicitly enabled. The operator owns these files and remains trusted; this does not isolate a process from the same privileged filesystem owner.

The validator's `--native-rpc-access-file` reads the bounded credential before binding HTTP. This mode refuses non-loopback binding, requires a constant-time capability match on every HTTP route before JSON-RPC/REST/genesis/snapshot handling, rejects duplicate credentials, browser Origins and query-bearing raw requests, and disables the unused raw WebSocket service entirely. The marker-enabled launcher always supplies that flag, including temporary no-voting tail-replay launches. There is no unprotected inspection RPC during managed recovery. Invalid credentials cannot be supplied in query strings or public profiles. Native transaction signatures and consensus rules do not change.

The gateway and dedicated faucet worker receive the raw capability through private operator files. The faucet ledger records that operator RPC is required, so a missing worker credential fails instead of retrying anonymously. The standalone tester CLI rejects operator credential options. Pinned public profile and package export copy only public network/endpoint identity and, when explicitly selected, the public local test CA. The capability, marker, reservoir seed, passwords, leaf private key and CA private key remain outside the archive. Operator clients also refuse redirects and proxy discovery.

Gateway sessions, invitation bindings, quotas, grant journals, original transaction signatures and fee caps remain independent of TLS process lifetime. TLS restart or leaf renewal cannot replenish an allowance or repeat a grant. A payment whose finality reply is lost must resolve its original pending signature and recover its recorded upload rent before another send. Certificate/startup failures leave original keys and journals intact.

This is a loopback-only operational rehearsal, not a public deployment. Public DNS, publicly trusted TLS issuance/renewal, firewall/container routing, dedicated service users, independent validators and monitoring still need deployment validation. Invited RPC access is not a consensus permission rule; public peer/TPU exposure would require its own deployment policy. A host administrator or filesystem owner can alter the launcher or read its credentials and is outside this admission boundary.

The internal authenticated raw HTTP hop assumes trusted local processes. Its capability blocks unauthenticated callers, but it does not authenticate raw-server ownership against a hostile process capturing a loopback port during downtime. A hardened shared host requires an authenticated private transport or OS network isolation; that boundary is not established by this local rehearsal.
