# Standalone wallets access the isolated service through invited HTTPS

The dedicated validator account is useful only if clients can use the chain without its private RPC capability. Run the existing invitation gateway, finite faucet and TLS listeners inside that account. Export an allowlisted public network profile with a pinned local test CA, HTTPS RPC at loopback 23898 and admission/faucet service at loopback 13780. The direct source profile, validator keys, RPC capabilities, faucet seed, funding passwords and admission ledger remain in the nontraversable service directory. Existing gateway method/origin/envelope checks, signed invitations, durable quotas and user-paid fees remain authoritative.

Standalone desktop wallets create and encrypt their own seeds outside the service account. Their signing/password input continues through the existing native wallet interface. The administrator exports only a public profile and one invitation into a new owner-only temporary file assigned to the desktop UID. Two fixed local acceptance clients reuse their original issued invitations instead of consuming fresh capacity on retries. This local procedure does not send invitations to other people.

Ingress setup explicitly creates one finite reservoir and two lifetime grant slots. Each setup value operation records its phase before submission. If interrupted, initialization refuses to resubmit or reinitialize: retain the original pending signature, staging record, gas signature and sponsor request for explicit recovery. The ordinary supervisor opens ingress only after the original setup reaches ready state and profile/admission pins validate. It never funds a reservoir or creates keys on restart. Worker or listener failure restarts the owned service group, recovering its original durable state.

The sealed bundle inventory advances to v2 with the faucet binary and gateway/TLS modules. The updater recognizes the exact legacy v1 inventory, rejects arbitrary added paths, verifies the pinned new bundle, retains all original private state and removes newly added code files during verification rollback. An intentionally paused service stays paused after an update. Administrators remain trusted; interruption during code replacement still requires explicit seal repair.

Testing uses one isolated two-validator network at a time. Low free disk space pauses writers instead of repeatedly restarting them; startup waits when less than 1.5 GiB is free and running service writers stop below 1 GiB. Those limits protect this local development machine, not a production capacity plan. The service is paused after bounded acceptance to limit CPU and disk use. The original wallet remains bound to its original genesis; funds and seeds are not silently migrated to a fresh chain.

Local pinned test certificates expire and are never installed in the OS trust store. Public hosting, external TLS and routing, uptime/backup operations, production capacity limits and independent cryptographic/security review remain separate work. Passing this local integration does not establish mainnet readiness or end-to-end pending-payment acknowledgement-loss recovery through the new gateway unless that scenario is separately exercised.
