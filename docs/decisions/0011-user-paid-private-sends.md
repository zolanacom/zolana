# 0011: Extend bounded user fee authorization to private transfers

Status: implemented and accepted locally; no deployment or publication

Private transfers already use the native NPAY0001 payment with zero public value balance and no public withdrawal destination. Its fee-payer field is bound into the proof authorization. The chain does not require that payer to be an operator. Extend the wallet's existing seed-derived fee account and durable cap to this shape without changing protocol bytes, consensus, features, staging accounts or nullifier rules.

The CLI accepts `send --fee-payer user --max-fee-debit <units>` alongside the existing user-paid withdrawal. `fees --payment send` quotes the exact 9,222-byte two-action upload and six-account finalizer. The default fee quote remains the 9,254-byte recipient-bound withdrawal for compatibility. Quotes identify their payment kind. No private recipient, amount or proof is needed for a send quote. The proof builder still validates the actual address/amount/available notes before proving and binds the selected payer to the signed payload.

The shared fee layer permits only zero-public-value sends or positive recipient-bound withdrawals. Negative public deposits, legacy public withdrawals without an independent destination, and inconsistent destination/value combinations are excluded from user-paid submission. CLI and device-local API reject mixed sponsor credentials/modes, invalid caps and unsupported quote selectors. Standalone tester profiles permit explicitly user-paid sends and keep operator deposits/sponsorship forbidden.

The existing staging journal carries the original payer, network, payload length/digest, gross cap, charged potential debits and cleanup reserve. No new recovery format or plaintext private-payment intent is added. Every charge persists before broadcast. Unknown finalization still blocks new sends and rent reclamation until full canonical RPC history resolves the original signed identity. Resolution cannot refund/reset the authorized charges, and cleanup derives the same fee key and original cap. Older withdrawal recovery records remain valid.

The wallet defaults private sends to user-paid fees, presents gas balance/address, refundable upload rent, permanent nullifier rent and the gross cap, and reviews these separately from the private value. Refresh/edit preserves recipient and amount. With explicit development sponsor credentials, a user can select the existing test sponsor; there is no fallback from an unfunded/failed user-paid send. Standalone Send is enabled, while automatic test-coin funding remains unavailable.

Using a public fee account links its transactions and funding on chain. Payment contents are shielded; fee account, timing, nullifiers and public deposits/withdrawals are visible. Fees and temporary rent must already be available publicly; this does not deduct gas from shielded notes or implement a faucet/bridge. Production fees/rent, independent review, network anonymity and external operations remain open.

Acceptance uses a fresh private local rehearsal and two standalone profiles. An explicit setup deposit and one fixed valueless fee grant per user precede sponsor-free operation. Operator vault/policy/reservation files are unavailable thereafter. A test-only helper restages an already accepted private-send proof under the same user's ordinary durable cap, checks native-owned nullifiers exist first, and requires a finalizer rejection. Its retained unknown/preflight journals are resolved canonically after blockhash expiry and cleaned up with the original authorization. It cannot fund deposits or send fresh proofs and is restricted to private loopback rehearsals and a separate restored replay-wallet path.
