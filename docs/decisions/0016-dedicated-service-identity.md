# Dedicated local macOS validator identity

Owner-only files and Unix sockets cannot isolate unrelated applications running under their owner's UID. The next local boundary is a separate no-login macOS account and primary group, with no administrator membership, login password or sudoers rule. Its validator identities, authorized voters, encrypted role material, passwords, RPC capabilities, journals and ledgers are generated inside a directory that the desktop UID cannot traverse. No private service key is copied through a desktop-readable staging bundle.

Account separation also requires immutable executable inputs. The installation copies an exact manifest of local binaries and required Python modules into a new root-owned directory. Non-root accounts cannot modify that code, configuration or launchd plist. The native binaries link only system libraries; the service uses the root-managed system Python with isolated import mode and a sealed module directory. It never executes the desktop-owned source tree, Homebrew Python or a user-provided command. An administrator-approved bundle and installer digest pin the installation before root execution. Missing/tampered/unexpected bundle files fail instead of being installed. Existing installations or unrelated account names are not adopted or overwritten.

The launchd system daemon drops to the dedicated UID/GID, applies umask 077, retains its validator children in the daemon process group and keeps the group alive. The supervisor checks original private policy, performs the same guarded coordinated restart and refuses missing towers, keys or credentials. SIGKILL recovery retains original pending signatures, nullifiers, ledgers, signed towers and budgets. Missing setup state never runs key generation automatically. Startup with a missing capability must fail closed; restoring its original file resumes its original network.

A fresh isolated fixture uses offset 5000: logical raw RPC 23899/24899, inspection 33899/34899, gossip 23000/24000 and nonoverlapping dynamic ranges. All network addresses remain loopback. Raw RPC serves only private Unix sockets with the existing peer-UID and capability checks. This leaves the user's existing wallet listener and legacy demo validators untouched. The legacy demo uses its original disposable network and keys; installing a separate service does not retroactively make those already published fixture keys secret or migrate the user's wallet to another genesis.

Privileged acceptance must test a desktop-UID process failing to open identity/voter/capability files, modify sealed executable inputs and connect to raw sockets before and after restart. The service itself builds real private payments, withholds an actual finalized reply, SIGKILLs the signing client, and verifies exact payment/nullifier recovery after launchd replaces the supervisor and both validator processes. It must also verify missing-credential startup refusal and original-file recovery. Unit tests and a prepared installer alone do not establish this boundary; administrator installation and actual cross-UID acceptance must be reported separately.

The administrator, kernel and all trusted programs within the service UID remain inside the trust boundary. No public deployment, existing key migration, global firewall/trust change or permission to impersonate unrelated accounts is introduced. Updates require a new digest-reviewed bundle and root bootstrap; they replace only manifest-listed code while the daemon is stopped, preserve all private state and restore the old code on verification failure. Account removal, public ingress deployment and independent security review require their own operational steps. Original private state must never be deleted as automatic cleanup or rollback.
