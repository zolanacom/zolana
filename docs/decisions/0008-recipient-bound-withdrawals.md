# Recipient-bound native withdrawals

The native exit must credit an address chosen by the user independently of the public fee sponsor. Previously NPAY0001 positive public value credited the sponsor. Keep those historical bytes and proofs replayable, but restrict the CLI's explicit `withdraw-legacy` operation to disposable fixtures. Guarded rehearsal sponsorship rejects legacy withdrawals.

NPAY0002 adds a 32-byte public recipient after the sponsor, a separately domain-separated authorization digest and a seventh writable finalization account. The Orchard proof and spend authorization bind network, genesis, sponsor, recipient, public value, anchor and expiry. Recipient substitution or converting the encoding back to NPAY0001 invalidates authorization. The proof circuit, pool state, permanent nullifier layout, finalize opcode and packet limit remain unchanged. A two-action recipient-bound payload is 9,254 bytes; ordered staged upload remains necessary.

A standard Agave feature account gates NPAY0002 execution. Fresh local genesis enables it; preserved networks, genesis hashes, policies, keys and history remain untouched. A deployment to an existing network needs coordinated validator upgrade and an explicit feature activation plan. Merely changing wallet configuration does not activate it.

The native processor accepts a matching writable, on-curve, non-executable system account with empty data, distinct from the sponsor. The resulting balance must meet the zero-data rent floor. Pool backing funds exactly the public withdrawal value; sponsor funds only transaction fees and permanent nullifier rent, with temporary staging rent recoverable. CLI preflight rejects invalid destinations and dust before reserving sponsor allowance. Execution repeats the checks atomically; a concurrent account change can still fail a transaction and consume fees.

By default the destination is an independent Ed25519 authority derived from the encrypted wallet seed using a domain-separated, network/genesis-bound keyed hash. Restoring the same seed restores that public signer as well as shielded keys. This public account is on this L1; it is not a Solana mainnet address balance or a bridge. Explicit public destinations are supported, but the wallet cannot establish that a supplied address belongs to the user. The wallet reviews the destination and discloses that the amount and destination become public. Reusing the default public account links withdrawals to one another.

The pending journal stores recipient, amount and sponsor before final broadcast. Resolution uses an uncached canonical full-history RPC scan to derive the actual receipt, checks saved intent and retains the journal on mismatch or missing history. Retained ciphertext archives can reconstruct notes after snapshot recovery, but cannot establish whether an unknown payment executed. Recovery never submits the withdrawal again. Upload cleanup continues to use the original durable sponsor reservation, including after lifetime allowance exhaustion.

New rehearsal policies explicitly allow bounded withdrawals; old policies without `max_withdraw` continue to deny them. New private fixtures use 5,000,000-unit test funding to permit withdrawals above the default 890,880-unit public-account minimum. These are development amounts and are not launch economics. Sponsor funding and availability are still operator-controlled; permissionless or user-paid fee submission needs separate product work. Native value authorization already belongs to the user's shielded spend key.

This change does not add a hosted wallet, public testnet, audited privacy, mainnet bridge or private trading. The public transfer acceptance utility is confined to a one-shot 10,000-unit local rehearsal check; it is not a production public-account transaction interface.
