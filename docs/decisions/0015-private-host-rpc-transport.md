# Private host transport for operator RPC

A reusable capability on loopback HTTP does not authenticate server ownership. Another unprivileged process can bind the validator's old TCP port during downtime. An operator client connecting to that port would disclose its capability. Hardened private rehearsals therefore use HTTP over Unix domain sockets directly inside the validator. There is no raw TCP relay or second TCP listener in this mode. Invited wallet RPC and faucet access remain verified HTTPS.

A structured, owner-only `native-rpc-unix-v1` credential contains the capability and an explicit mapping of logical RPC ports to canonical absolute Unix socket paths. The logical HTTP URL remains a selector for a pinned route; it does not open a TCP connection. Both Rust reqwest clients and Python operator forwarding select Unix transport exclusively when that credential is structured. Missing routes, missing sockets, wrong socket types, symlinks, shared permissions or unavailable directories fail instead of selecting TCP. The faucet copies the whole credential and records a durable `operator_unix` policy bit so a legacy source credential cannot silently downgrade its transport at restart. Public profiles and tester archives do not contain this operator material or routing metadata.

Each socket resides in a directory owned by the effective UID and accessible only to that UID (0700), with an owner-only socket (0600). Canonical parent checks refuse symlinked parents. Every ancestor must belong to root or the operator; writable shared ancestors are refused unless sticky-directory rename protection applies. This prevents another UID from replacing an entire socket directory between a path check and a connection. The validator checks the connecting Unix peer UID before parsing HTTP and retains the constant-time capability guard on every RPC, REST and file route. Raw WebSockets remain disabled. Connections are bounded to 64, carry one HTTP request each, use a 30-second deadline and are canceled during shutdown. Disabling keepalive prevents an absolute connection deadline from interrupting a later request on a reused operator connection. The existing upstream JSON-RPC HTTP handler runs directly over Unix streams, preserving native request processing and body size limits without another server fork or dependency.

A private lock file holds an exclusive advisory lock for the socket's whole lifetime. Startup refuses an existing live socket, unsafe object or shared lock file. A retained socket whose connection is refused can be removed only while that lifetime lock is held. Normal shutdown removes only the inode/device created by that listener; it never removes a replacement pathname. SIGKILL releases the OS lock while retaining the stale pathname, allowing the same original private credential and policy to recover safely. No funds, private keys, journals, towers or ledgers are replaced to repair transport.

A permanent marker pins the entire structured credential digest and the enabled network policy. Managed launch checks require the original transport, exact normal/inspection route mapping and credential; no-voting replay inspection uses the same protected validator path with its own pinned Unix route. Existing fixtures keep their original policy; hardened acceptance creates a fresh private root. Upgrading an already funded policy is deliberately not automated.

This boundary isolates raw RPC from network clients and processes running as other unprivileged OS users, and closes TCP port impersonation even by a process sharing the operator UID. It does **not** isolate the operator's keys or Unix sockets from another process with that same UID, or from the host administrator. Those principals can read or change private operator files. A dedicated service account or VM/container boundary with separate ownership is required before treating unrelated same-user programs as hostile. No OS users, firewall rules, trust stores or public services are installed by this local rehearsal. Gossip/TPU exposure and validator consensus admission are separate deployment concerns.
