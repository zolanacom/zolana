# Preserve fork records while coordinating a native restart

The original installed service stopped at a startup inspector, before any voting process launched. Ledger 0 retained the shared signed vote/frozen bank at slot 6174, incomplete children 6175 and 6179, and a full unfrozen competing block 6176 whose parent was 6171. An older rejected block 6156 was marked dead and had no frozen bank hash. Ledger 1 had the same voted bank and an incomplete 6175 child. Treating every intermediate or dead record as an unrecoverable tail conflated these different cases.

The restart inspector now traces ancestry from the original signed vote and selects its highest complete, already-frozen descendant. The checkpoint must retain the rooted ancestry, match the stored bank hash and sit above the blockstore/tower/snapshot root. Missing or invalid selected ancestry, a rejected selected bank, frozen/dead contradictions, duplicates and excessive inspection ranges fail closed. Existing rejected forks and descendants stay rejected; all competing, partial and compatible complete blocks remain stored. No shred, bank hash, dead/duplicate flag, key, genesis or tower is removed or rewritten by the planner.

The first simultaneous SIGKILL exposed a distinct persistence boundary: the majority had saved the frozen hash and signed vote for 6271 before its final broadcast shred batch reached disk. Its 6271 metadata and the peer's copy were incomplete; both retained the complete frozen ancestor 6270. In this case the planner can select the closest complete frozen ancestor on the exact signed-vote branch, strictly above both roots. It still verifies the signed vote's own stored hash and keeps that vote, every partial record and all lockouts. Agave's existing future-tower restoration handles the vote beyond the replay checkpoint. It cannot choose a competing complete fork, clear the future vote, pass a root-reaching checkpoint or rebuild an empty tower. A second no-voting private-copy replay verified this specific crash state with both original signed tower byte strings unchanged.

Replay must also preserve the distinction between a restored future vote and a replayable bank. In native checkpoint mode, `ReplayStage` defers creating an in-memory Bank for an incomplete stored slot that already has a frozen hash. Otherwise that partial Bank supplies apparent ancestors for the saved vote, concealing its stray-restored status and stalling ordinary fork choice. Its metadata, shreds, hash and tower remain stored, repair remains enabled, and a completed slot is admitted through the usual verified replay path. Complete competing descendants remain competing even when they share the selected ancestor with the incomplete voted branch. Default startup does not enable this deferral.

Native replay also captures the existing ledger-slot inventory before its producer can create new Banks. Complete historical local-leader blocks are replayed through the normal verifier; they cannot use the live TPU shortcut that assumes this process already executed them. Any stored frozen hash must match before it can be replaced. Live producer slots, including previously empty gaps below the old tip, are absent from that captured set and keep the normal shortcut. A cached hash on an incomplete orphan remains retained after voting moves to another branch.

Managed validators additionally use `--native-durable-votes`: a new vote is recorded only after the candidate's block data and every required unrooted ancestor are complete in local blockstore. This prevents the original final-broadcast-batch race from creating another signed vote whose data cannot be replayed after a process crash. Rooted snapshot ancestry is excluded from this data check. This is process-crash protection; filesystem/power-loss durability still needs separate coverage.

Filling an epoch's remaining slots while roots lag can exhaust the root-derived leader schedule before new votes can land. The optional `--native-restart-epoch-horizon` requires a slot/hash-pinned frozen ancestor shared by both stopped identities' checkpoint ancestries. Its stake schedule can open at most one additional epoch. Verification may warm that schedule at the exact hash-checked ancestor before replay crosses the boundary; production still waits for the selected checkpoint hash and coordinated stake gate. Once ordinary finality catches up, the cache checks the schedule against the actual rooted Bank and removes the allowance. Ledger roots, stake, signed towers, genesis and payment rules are unchanged. Different tips can share a valid anchor; a future-epoch complete child is retained for this native verified path instead of guessed offline inspection scheduling. This custom coordinated startup policy requires independent runtime/consensus review before external deployment.

The supervisor waits for both peers to finalize beyond the entire pre-start stored tail before running history collection or opening wallet ingress. An RPC socket or readable replay checkpoint alone is insufficient: finalized account context and rooted block history can differ during startup. The wait is finite, respects the finite rehearsal session, and leaves the original state paused on failure. Collector failures retain bounded diagnostics inside the private service directory; they never publish a replacement archive or weaken proof/continuity checks.

Managed coordinated launches use the explicit validator flag `--native-restart-checkpoint`. It bounds initial blockstore processing at the frozen checkpoint before the stake barrier and original tower restoration. It does not configure an inspection halt or permanently stop replay. Ordinary verified replay and fork choice handle remaining records after startup. The flag requires the original tower, expected genesis, expected frozen bank hash and coordinated wait slot. It rejects warp/hard-fork/inspection overrides, a loaded root reaching the checkpoint, or advancing past the checkpoint before the barrier. It also refuses the upstream hard-fork path that would discard tower restoration. Startup without this opt-in retains upstream behavior.

A single direct full child can still use the prior separate no-voting replay path when the stopped peer already has its exact frozen hash. Multiple or uncorroborated complete descendants are retained for native checkpoint startup, never executed offline by guessing a hash. Planning remains exclusive PRIMARY blockstore access with stopped validators.

Before applying this to original ledgers, APFS copies had independent file inodes, validated snapshot links remapped inside their copy, copied original signed towers and no routes back to original ledgers. The selected original checkpoint replayed without voting; every copied retained shred/frozen hash and both signed tower byte strings stayed unchanged. A copy of a validator identity must never run as a voting peer alongside its original.

This controls a development two-validator restart. It is not a general operator repair command or permission to reset a damaged ledger. A deployment still needs review of runtime changes and coordinated operational procedures.
