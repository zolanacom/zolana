# Public TLS certificate deployment

`tools/public_tls_certificate.py` verifies and snapshots the publicly trusted certificate issued for the pilot gateway's public IPv4 address. The address is operator configuration: pass `--public-ip <public-ip>` or set `ZOLANA_PUBLIC_IP`; no address is built in. It changes certificate files only. Existing authorities, wallets, claims, invitation slots, profiles, budgets and validator ledgers remain separate. This runbook describes the code; an issued certificate or passing unit test does not establish external gateway acceptance.

The root-only Linux `deploy` command reads only `/etc/letsencrypt/live/<public-ip>/{fullchain.pem,privkey.pem}`. Those two root-owned leaf symlinks must resolve to matching numbered, root-owned regular files under `/etc/letsencrypt/archive/<public-ip>/`; all directory ancestors must be root-owned, real and not writable by other users. A Certbot `RENEWED_LINEAGE` value must equal that exact lineage. No private key leaves Linux or appears in the JSON result.

Before publishing, the helper captures the bytes and verifies their full chain against normal `/etc/ssl/certs` roots using the IP SAN and server purpose, requires at least3600 seconds of remaining leaf validity, compares the certificate and private-key public components, and creates a TLS1.2-or-newer server context from the same captured bytes in a private temporary directory. It prints only metadata and hashes. The service calls `verified_context(cert,key,public_ip,expected_uid,minimum_validity=3600,trust_directory='/etc/ssl/certs')`, which returns `(SSLContext, metadata)`. Metadata fields are `certificate_sha256`, `key_sha256`, `public_ip`, `not_after`, `not_after_unix` and `minimum_validity`. The trust-directory override exists for pure test fixtures; the production adapter always uses normal roots.

Deployment takes an exclusive root600 `deploy.lock`. New bundles are exclusive directories under `/etc/zolana-native-074/tls/bundles/<positive-sequence>/`; directories are root-owned755, and `server.crt` and `server.key` are UID994 mode600. The root444 `/etc/zolana-native-074/tls/current.json` contains exactly `format`, `sequence`, `certificate_sha256` and `key_sha256`, with format `zolana-public-tls-bundle-v1`. Files/directories are synchronized before the manifest is atomically replaced and its parent synchronized. Old bundles and interrupted unpublished bundles are retained. A retry skips retained orphan sequence numbers; it never deletes a bundle or overwrites a prior version. An unchanged verified pair leaves the current manifest unchanged.

After separately reviewing and installing the sealed script, root invokes its fixed command:

```sh
python3 -I -B /opt/zolana-native-074/tools/public_tls_certificate.py deploy --public-ip <public-ip>
```

An explicit `--restart-active` additionally uses `systemctl try-restart` for **only** `zolana-native-060-gateway.service` if it is already active and running, then checks a fresh active invocation. It never explicitly targets the validator and never starts an inactive gateway. The explicit reload is attempted even when the manifest is unchanged, allowing recovery if an earlier publication succeeded but its restart failed. With no flag, unchanged deployment is a strict no-op. The renewal deploy hook should invoke this fixed command after a newly issued certificate; it must not point the service directly at changing Certbot symlinks. Coordinate manual reloads with any bounded acceptance lifecycle, whose original-invocation guards otherwise correctly reject a surprise restart.

Focused local validation uses `python3 -B -m unittest discover -s tools -p public_tls_certificate_test.py`. Eleven tests cover real isolated CA/IP/key/expiry verification, exact-byte capture despite later source-file mutation, malformed manifest rejection, atomic publication interruption/orphan recovery, unchanged deployment/reload behavior, root guard and exact fixed gateway command. Publisher privilege boundaries are mocked only inside disposable non-root filesystem fixtures; these are not live root-deployment or crash-recovery results. Mac's system LibreSSL lacks the required IP verification option, so the test fixture uses the available OpenSSL3 executable; production fixes `/usr/bin/openssl` on Linux. No trust store is modified.
